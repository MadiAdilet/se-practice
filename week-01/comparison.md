## 3. What the AI added that I never asked for

- A configurable "Pass threshold" slider (default 50%) instead of a fixed ≥50 rule from the spec — this makes the pass/fail result dependent on a setting the user could accidentally change.
- A full web UI (input box, sliders, buttons, cards) instead of a simple console program — the one-line prompt only asked to "print" results.
- Six stat cards, including "Passed" and "Failed" counts, when the spec only required a single pass rate percentage.
- A mark-distribution histogram (bar chart) — not requested.
- Sorted, color-coded "Parsed Marks" chips (green for pass, red for fail).
- A "tokens detected" counter next to the input field.

## 4. What the AI got wrong or silently skipped

- **Incomplete range validation:** with input `88, 47, 23, 32, 101, -5`, Rocket correctly rejected `-5` (below range) but incorrectly accepted `101` (above range) as a valid mark, reporting "5 marks processed" and Highest: 101. Expected: 4 valid marks, Highest: 88. This is exactly the boundary case the assignment spec warns about.
- **Silent failure on mixed valid/invalid input:** before the fix, pasting a list containing invalid tokens alongside valid ones (the original case B string) produced no visible result at all, rather than either an error message or processing just the valid marks.
- **Misleading zero-statistics on empty input (case D):** instead of a clear "no valid marks" message, Rocket displayed a full results panel with every stat set to 0 — a reader could easily mistake this for "5 students, all scored zero" rather than "no valid data was found."

## 5. The defect I asked Rocket to fix

**Prompt I used:**
```
The app treats marks above 100 as valid. For example, entering
88, 47, 23, 32, 101, -5 shows "5 marks processed" and Highest: 101,
but 101 is outside the valid 0-100 range and should be excluded.
Only marks where 0 <= mark <= 100 should count as valid. Please fix
the validation so marks above 100 are rejected the same way negative
marks already are.
```

**Result:** Fixed. Valid count changed from 5 to 4, Highest changed from 101 to 88, Average recalculated correctly from 58.20 to 47.50. No other visible regressions.

**What this tells me:** The AI's first implementation checked the lower bound of the valid range (rejecting negatives) but forgot the upper bound (accepting >100) — a classic incomplete-validation bug that a vague one-line prompt didn't surface until I tested the boundary explicitly. It only got fixed because I gave it a precise, concrete counter-example rather than a general "check the validation" request.

## 6. Reflection (200–300 words)

The AI genuinely sped up writing the actual logic of the program — going from a one-line prompt to a working implementation of averages, highest/lowest, and pass rate took far less time than writing and debugging that logic by hand. In that sense, Rocket did real work, not just scaffolding.

Where it cost me was the validation boundary: the app correctly rejected negative marks but silently accepted marks above 100 as valid, which changed the average and the highest score without any warning. It looked confident and correct in the UI — clean cards, a specific number — right up until I tested a value outside the range on purpose. That is exactly the kind of bug that looks fine at a glance and only breaks on the case you didn't think to try. The same pattern showed up again on case D, where instead of admitting "no data," it displayed a full panel of zeros that could easily be mistaken for real results.

I would put my name on both artefacts, but with different levels of confidence. The manual version I can defend completely — I wrote every line, I know why the validation works, and I verified it matches the spec by tracing it by hand on all four cases. For the Rocket version, I never saw the actual code — only the UI and the numbers it produced. I could verify the outputs against the spec, and I did find and get a real bug fixed, but I could not verify how it computes those outputs, so I can't fully vouch for it the way I can for code I wrote myself.

What this experiment tells me a human engineer still has to own — regardless of who or what wrote the code — is both things equally: testing edge cases against the exact spec, and being able to explain the code line by line. Rocket's app looked done well before it was actually correct. Catching that required deliberately designing test cases at the boundaries, not just trusting the first result that appeared.
